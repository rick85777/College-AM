# College-AM 可行性分析报告

> 分析日期：2026-11-24　|　分析对象：College-AM（大学生考证/竞赛/招聘信息聚合开源网站）
> 方法：5 人研究组并行作业（竞品 / 信源合规 / 技术架构 / 产品运营 / 红队评审），全部结论用一手 URL 实证，红队复测 40+ 引用点。
> 分报告：`docs/research/01~05`

---

## 一、一句话结论

**方向成立，但你现在描述的产品形态是错的。**

"聚合所有大学生考证/竞赛信息 + 专业板块 + AI 板块 + 招聘跳转 + 移动端 + 桌面端"这个完整形态，**不建议做**——它会在第 6 个月死于"没人有理由打开"。

但把同一个内核收窄成 **"可核查的报名时间轴 + 日历订阅"**，只做 3 门考试、只服务 1 所学校，**8 周内可以验证出真假**，成本不到 2000 元。

一句话：**先验证"有没有人愿意把截止日记进日历"，再谈网站。**

## 二、三个必须先知道的事实

### 2.1 你想模仿的 AIHOT，引擎是开源的——这条改变了整个起点

| 事实 | 数据 | 来源 |
|---|---|---|
| 仓库 | KKKKhazix/AIHOT | github.com/KKKKhazix/AIHOT |
| 协议 | **MIT**（可商用、可闭源改造） | 仓库 LICENSE |
| 热度 | **11,340★ / 2,631 fork** | GitHub API 实测 2026-11-24 |
| 技术栈 | TypeScript + Node 24 + PostgreSQL 17 + Docker Compose（db/setup/api/worker/web 五容器） | README |
| 运行成本 | 示范信源首次导入 152 条 ≈ 930 次模型调用；日报按规则编排**不调模型** | docs/deploy.md |
| 作者背景 | 设计师出身，半年前看不太懂代码，代码是与 AI 一起重写的 | README 自述 |

**能直接复用的**：六种信源适配器（RSS / 网页列表 / JSON 接口 / X / 公众号 / 自建推送）、信源三级分层、预筛 + 双次独立打分、事件聚簇、日报编排、RSS/API/MCP 三件套、后台与试抓预览。

**不能照搬的**：它的模型是**高频日更**（AI 圈一天几十条，日报有存在理由）。**考证/竞赛是低频强周期**，一年就 3 月、9 月两个窗口——套用日报模型，等于用一台印钞机印一张贺卡。

> **落地建议**：直接 `Use this template` 起一个仓库，砍掉日报/周报/热点榜，把"每天出刊"换成"每个报名窗口前 30 天提醒"。这一步能省掉 70% 的从零开发。
>
> **但有一条要警告**：AIHOT 的 MIT 协议允许你闭源改造，也意味着**别人可以原样抄走你的站**。你的护城河不在代码，在数据与一贯的可核查性——这也是为什么下面第四章（信息源可靠）比第五章（技术架构）重要得多。

### 2.2 赛道上已有四类玩家，唯一的空隙是"时间"

| 玩家 | 代表 | 它解决了什么 | 它没解决什么 |
|---|---|---|---|
| 赛事聚合/报名平台 | 赛氪（3 万+ 竞赛，报名 SaaS）、我爱竞赛网（Discuz 论坛改的门户）、竞赛通知网（115 个竞赛 + 报名日历） | "有没有这个比赛、什么时候报" | 时间字段不结构化、不可订阅；赛氪卖报名、我爱竞赛网卖广告、竞赛通知网卖**辅导**——信息都只是获客入口 |
| 官方权威源 | NEEA 四站、软考、人事考试网、学信网、ncss.cn | 各自领域的**权威**报名与查分 | **各自为政，没有跨部门的考证日历** |
| 求职平台 | 牛客、实习僧（2100 万学生）、BOSS、智联校园 | 求职与笔试 | 完全不覆盖"考证/竞赛"这一层 |
| GitHub 开源同类 | 见 2.3 | 单点工具 | 无一做到持续维护 |

**唯一可站的位置**：**跨部门的横切时间轴 + 每条都能点回官方原文**。官方源在权威性上不可战胜，但在"横切 + 时间轴 + 可订阅"上是空白。

⚠️ **不要碰的两块**：① **考研信息聚合**——学信网/研招网已经收编；② **校园招聘聚合**——ncss.cn 已把省级、校级就业网做成可切换分站，且有 2100 万用户级的商业对手。这两块都会被正面碾过。

## 三、需求真实性：一半有硬证据，一半是空的

### 有证据的一半（供给侧碎片化可测量）

同一件事——"我这个专业未来 3 个月有哪些证和赛要报名"——学生至少要跳 **6 个互不相通的系统**：

- NEEA（四六级/计算机 NCRE/教资 NTCE，各自独立子站）
- 软考官网 ruankao.org.cn（报名时间表在 bm.ruankao.org.cn，**31 省表格，是全项目结构化程度最高的一页**）
- 人社部人事考试网 cpta.com.cn（专业技术人员资格，72 项国家职业资格目录）
- 学信网 / 研招网（考研）
- 本校教务处（**杭电"学科竞赛"栏目 205 条记录、15 页，且与获奖名单混排**；上海交大教务处首页 30 条里没有一条竞赛报名——散在创新创业学院、团委、各学院）
- 主办方官网（数模 mcm.edu.cn、蓝桥杯 dasai.lanqiao.cn……）

**规模侧**：2026 年全国大学生数学建模竞赛 **1,963 所院校、89,543 队、26 万多人**报名（mcm.edu.cn 首页实测原文）。单个赛事峰值需求极大，且**集中在时间窗口**——这正是日历型产品的最优场景。

### 没有证据的一半（必须诚实标注）

**没有任何公开的、可引用的大学生信息获取渠道调研。** 关于"信息差"的内容几乎全是自媒体转述。

所以目前只能证明：**供给是碎的**。不能证明：**学生愿意为此换一个网站。**

> 这一条直接决定产品形态：**别做"内容站"（靠流量变现），要做"工具"（靠日历订阅与嵌入式使用）**。工具的价值不需要用户"信任一个新媒体"。

## 四、你的注意点 1：确保信息来源可靠 —— 怎么才算真的可靠

这是全项目最硬的一节，也是唯一能形成壁垒的地方。

### 4.1 四层信源体系（写进数据模型，不是写进口号）

| 层级 | 定义 | 采信规则 | 复核频率 |
|---|---|---|---|
| **L1 官方** | 主办方/主管部委一手发布口 | **唯一可直接支撑"报名时间/费用/考试日期"的层级** | 报名季每日；平季每周 |
| **L2 半官方** | 高校教务处/研究生院、省级考试院 | 只能佐证，不能单独定案，必须回链 L1 | 学期初每周 |
| **L3 可信媒体** | 中青报、上观、人民网教育 | 仅作线索，不作事实来源，必须回溯 L1 | 不主动巡检 |
| **L4 用户投稿** | 站内纠错、补充 | **永久不能成为任何条目的唯一来源** | 48h 内处置 |

**置信度上限由层级决定**（L1=100 / L2=75 / L3=50 / L4=40 且不可发布），用代码 `min(score, cap[tier])` 强制，不靠自觉。

### 4.2 实测结论：官方源的可抓性远好于预期，但"结构化"几乎为零

抽查 30+ 个官方入口的实际结果：

| 结论 | 数据 |
|---|---|
| **无一个源提供 RSS / 公开 API** | 抽查 16 个源首页，0 个有 feed，0 个有文档化 API |
| **约 60% 是纯静态 HTML，可零成本直取** | NEEA 四站（cet/ncre/ntce 首页 18-20KB 静态）、软考两站、人事考试网、会计评价中心、中注协、数模、创业服务网、ncss.cn |
| **必须上无头浏览器约 20%** | 研招网列表、蓝桥杯（**首页仅 1,437 字节的 SPA 空壳**）、华为认证、国聘 |
| **完全不可抓约 20%** | 雅思考/托福（robots `Disallow: /` 全站禁抓）、挑战杯（**明确 Disallow GPTBot/ClaudeBot/CCBot/Bytespider**）、CPA 报名系统、人社部、公务员局 |

**最佳样板**：`bm.ruankao.org.cn` 的省级报名时间表——**静态 HTML 表格，覆盖 2020-2026 共 14 个批次，31 省报名/缴费时间可直接解析**。它证明了"官方表格可以被规则抽取"。

**合规上必须硬编码跳过的域名**：`ielts.neea.cn`、`toefl.neea.cn`、`tiaozhanbei.net`（项目库）。技术上能绕，法律与道义上都不该绕。

### 4.3 真实性保障机制（这是产品的核心卖点，也是唯一可验证的证据）

**每条信息强制显示四要素**，缺一不可：

```
来源：中国教育考试网 · 全国大学英语四六级考试（CET）  [L1 官方]
原文链接：https://cet.neea.edu.cn/html1/report/2609/1-1.htm ↗
抓取时间：2026-11-24 09:12 (UTC+8)   人工复核：2026-11-24 14:30
可信等级：A（官方原文直证）            [信息有误？]
```

**四条工程硬约束**：
1. 数据库**不存正文全文**，只存 `title + 自写摘要(≤80字) + source_url + fetched_at + 结构化字段`
2. 附件（PDF 大纲、职位表）**只存 URL，不镜像不转存**
3. 招聘模块**不设投递动作**，只有 `<a rel="nofollow noopener" target="_blank">`
4. 抓取器内置 robots 解析 + 域名黑名单

**红队修正的一个关键设计错误**：原方案要求"L1 直证 **且** 第二独立源一致"才可发布。但 **CET 报名通知、软考报名表、教资日程在现实中只有一个发布口**——第二独立源根本不存在。照此执行，首页"正在报名"将长期为空。

✅ **改为"同源二次校验"**：原文快照 + 附件哈希 + 发布日变更检测 + 强制跳转官方原文。**置信度不再决定"发不发"，只决定"标不标待核验"。**

**十类必须人工确认、禁止自动发布**（在数据库打 `manual_only=true`，Publish 环节硬拦截，与置信度解耦）：

1. 报名费用金额（分省定价、逐年调整、常在附件表格里）
2. 报名起止时间（CET 明确"各考点报名时间不同"，**全国统一时间不存在**）
3. 考试日期/批次安排（可能延期、分批）
4. 报考资格与学历/专业限制（错判一条会让人白准备一年）
5. 政策性优惠（单独划线、免试、加分）
6. 竞赛晋级规则、获奖名单、赛区划分
7. 招聘岗位的薪资、学历要求
8. 任何"取消/延期/辟谣/声明"类公告（误传即造谣）
9. 含个人身份信息的名单（法律红线，一律不入库）
10. 考点变更、准考证打印入口开放

## 五、你的注意点 2：自动化更新检索 —— 能自动到什么程度

### 5.1 技术链路（已验证可行，成本约 80 元/月）

```
Source Registry(sources.yaml) → Fetcher(HTTP优先/Playwright白名单) → snapshots(原始快照+raw_hash)
  → Parser(规则模板→LLM兜底) → Normalizer(日期/金额/机构归一) → Change Detector(三级哈希)
  → Dedup(实体对齐) → Confidence Scorer → Review Queue → Publish → field_changes + Index
```

**技术选型（不是性能问题，是"1-3 个人能不能长期维护"问题）**：

| 层 | 选择 | 理由 |
|---|---|---|
| 主干抓取 | **Crawlee 3.x + Cheerio**（纯 HTTP） | 与主站同为 TS 栈、单进程、依赖少。1.5 万页/月平均 21 页/小时，**吞吐根本不是瓶颈** |
| SPA 兜底 | **Playwright 1.65**，仅白名单 10-15% | 全量用会让 2C4G 打满且更易触发风控 |
| 禁止 | Scrapy | 为一个用不满 1% 的性能引入 Python 第二技术栈，负收益 |
| 第三方 API | Firecrawl，**仅作故障期应急取证** | $83/月按年付；数据出境 + 延迟 2-8 秒 |

**三道哈希，只有 `field_hash` 变化才发布**：

| 哈希 | 对象 | 作用 |
|---|---|---|
| `raw_hash` | 原始响应体 | 判断有没有拿到新东西 |
| `content_hash` | 正文容器纯文本 | 判断正文变没变（改版检测） |
| **`field_hash`** | 归一化后结构化字段 | **唯一触发下游发布的信号** |

这条规则把"页面换了备案号/banner"这类噪声压掉 90% 以上——用户不会一周收到 8 条假更新。

**模板失效告警（比 diff 更重要）**：页面改版的第一症状永远是"列表条数变成 0 或 1"，而不是报错。三个指标任一越界即告警：
1. `selector_hit_ratio` 连续 3 次 < 0.6
2. `item_count < guards.min_items`（如从 20 掉到 1）
3. `byte_size` 相对 30 天中位数偏移 > 60%

**成本**：**约 80 元/月** — 服务器 60 元（2C4G 轻量，按 33 个已验证源、约 4,000 页/月）+ DeepSeek 18 元（缓存命中 0.02/0.04 元、未命中 1/2 元、输出 4/8 元每百万 token，实测核算）。
> ⚠️ 红队指出原方案按"120 个源"算出 110 元/月是拍脑袋——实际只验证了 33 个源，其余 87 个没有任何清单。详细重算见 `docs/CHANGELOG-红队修订.md` M4。

### 5.2 但红队指出了一个致命问题：你自动化的恰好是最不值钱的字段

- **能自动发布的**：标题、URL、发布日期、主办方
- **必须人工的**：报名起止、费用、报考资格、考试日期（也就是用户真正用来决策的字段）

于是"降低 70% 人工"降低的是**录入标题的成本**，不是**决策成本**——而标题本来就不值钱。

**真正的瓶颈不是技术，是人**：**4-6 小时/周**（旺季 8-10 小时），单人能维护的上限是 **100-300 条**，超过 500 条必崩。

✅ **修正后的定位**：接受"**半自动**"。把人力集中在每年 **3 月 / 9 月两个窗口集中录入**（一年两次、每次两天），其余时间只跑 diff 巡检。**不要为"全自动"再造一层审核台。**

### 5.3 其余工程修正（红队发现，必须改）

| 问题 | 错误 | 修正 |
|---|---|---|
| 置信度公式三套并存 | 02 用 0.40/0.30/0.20/0.10，03 用 40/25/20/10/5，阈值 85/60 vs 85/70 | **以 03 为唯一口径**，02 的层级上限改为代码 clamp |
| 去重会误合并 | `0.5×name + 0.3×org + 0.2×year` 在阈值 0.86 时，同主办方同年份只需 name≥0.72 就自动合并（蓝桥杯软件类/电子类会被并成一条） | 阈值提到 **0.93**，或 org/year 改门控条件；同组织者+同年**强制人审** |
| 唯一键与"一年两轮"冲突 | `UNIQUE(program_id, year, round)` + `round DEFAULT 'main'`，CET/NCRE/教资第二轮写不进去 | round 用 `h1/h2`，或把 `signup_start` 并入唯一键 |
| 双许可与 DCO 互斥 | 04 承诺"作者保留商业授权"，又选 DCO 而非 CLA——DCO 不授予版权再许可权 | 改 **CLA**，或放弃双许可，变现改为"托管 + 商标" |
| 源数量是拍的 | 03 按"120 个源"算成本，02 只验证了 33 个 URL | 成本按 33 源重算，其余单列"待验证" |

## 六、致命风险：低频（四份报告里最该被重视的一条）

### 6.1 死因不是技术，不是成本，是"没人有理由打开"

- 四六级、教资、软考、考研，**一年各两次窗口**
- 一个学生真正需要这个网站的**天数，一年不超过 40 天**
- 剩下 320 天，产品没有任何打开理由

### 6.2 更反直觉的：.ics 订阅是最强的"卸载器"

用户把日历导进手机后，**系统级提醒就替代了你的网站**——他再也不回来了。

于是出现这个死循环：
> **订阅数涨 → 访问不涨 → 传播为零 → 6 个月后团队按自己的红线自我否决。**

### 6.3 两张表必须一起看

| 指标 | 现实预期 |
|---|---|
| GitHub Star（3 个月） | 50-150 |
| GitHub Star（12 个月，无大 V 转发） | **大概率停在 1k 以内** |
| 真实订阅（6 个月） | 200-400（乐观） |

**Star 与真实用户几乎不相关**——很多 5k star 的聚合项目没有一个日活。

### 6.4 成功率量级（红队判断）

| 目标 | 概率 |
|---|---|
| 做成"1,000 个真实订阅的工具" | **10-15%** |
| 做成活过一年、5+ 外部贡献者的开源项目 | **3-5%** |
| 能养活人的商业 | **< 1%** |

## 七、可行性评分

| 维度 | 评分 | 说明 |
|---|---|---|
| 需求真实性 | ★★★☆☆ | 供给碎片化有硬证据；"愿意迁移"无证据 |
| 竞品空隙 | ★★★★☆ | "跨部门时间轴 + 原文可核查"确实是空白 |
| 技术可行性 | ★★★★★ | AIHOT 已跑通同构方案，MIT 可复用，80 元/月 |
| 信息源可靠可实现性 | ★★★★☆ | 60% 静态可抓；但 20% 关键源必须人工 |
| 自动化程度 | ★★☆☆☆ | 只能做到"半自动"，核心字段必须人工 |
| 合规风险 | ★★★☆☆ | 索引+跳转可控；一旦做投递闭环即需人力资源服务许可证 |
| 持续运营可行性 | ★★☆☆☆ | 单人上限 100-300 条；4-6 小时/周；低频导致动力衰减 |
| **综合** | **★★★☆☆（6/10）** | **可做，但必须换形态** |

## 八、建议方案：8 周单点验证，而不是 6 个月建站

### 8.1 砍到最小

| 做什么 | 不做什么 |
|---|---|
| 只做 **3 门**：四六级 CET + 软考 + 教资 NTCE | 不做 20 个专业频道 |
| 只服务 **1 所学校**（你自己的学校） | 不做全国覆盖 |
| 只交付 **1 个 .ics 链接 + 1 张期末报名表** | 不做首页、搜索、AI 板块、招聘板块 |
| 只做 **1 个赛季**（下一个报名窗口） | 不做 App、不做桌面端 |

**为什么先砍**：真正的资产不是代码，是"**有人愿意把截止日记进自己的日历**"。在这条被验证之前，02 和 03 的所有复杂度都是负债。

### 8.2 8 周验证的验收线

| 周 | 动作 | 验收 |
|---|---|---|
| W1-2 | 手工整理 3 门考试的完整时间线（30-50 条），写成 `.ics` | 字段准确率 > 95%（抽检 20 条对官方原文） |
| W3-4 | 在自己学校 2 个学院群投放，只发"**我把你们学院这学期能报的考试整理成日历了，要吗**" | **50 人订阅** |
| W5-8 | 加 1 个自动化源（bm.ruankao.org.cn 省级表格），观察维护工时 | 周维护 < 2 小时；**累计 200 人订阅** |

**判定**：
- ✅ 8 周内 **200 人主动订阅** → 值得做，进入 M1
- ❌ 不到 100 人 → **停**，省下的是 3 个月而不是 3 年

### 8.3 如果验证通过，再按这个路线走

| 里程碑 | 周期 | 交付 | 通过标准 |
|---|---|---|---|
| **M0 数据骨架** | 4-6 周 | schema v0.1、10 个信源、50 条 Program、抓取链路 | 连续 14 天抓取成功率 > 90%；抽检 20 条准确率 > 95% |
| **M1 可用 MVP** | +6-8 周 | 100 Program / 200 Edition、5 个频道、搜索、.ics、来源页 | 真实用户 100、周活 30、.ics 订阅 20、处理 3 条真实纠错 |
| **M2 社区化** | +3 个月 | 开放投稿、共建人制度、schema v1.0 冻结 | UGC 通过率 > 60%、30 日留存 > 15%、2 个频道有外部共建人 |

**注意红线要改**：原方案写"6 个月拿不到 1000 订阅就退回纯开源"——按上面的节奏这**不可能达成**，项目会被自己的红线判死。改为 **"6 个月 200，12 个月 1000"**。

### 8.4 你原方案里几个具体设计，逐条给结论

| 你的想法 | 结论 | 理由 |
|---|---|---|
| 按学院分板块（信息工程学院/软件学院…） | ⚠️ **改** | 学院是组织单元不是需求单元：多数学校"信工=计算机改名""软件学院=同一套师资"，会出现 3 个 90% 重复的空页。**改为按"职业出口"分 12-15 个频道**（后端开发/算法/嵌入式/网络安全/考公/保研/财会/教师…），学院名只作为 `aliases` |
| 频道上线门槛 | ✅ 采纳 | 一个频道要上线需 **≥8 个 Program（≥3 证 + ≥5 赛）**，且 ≥60% 有 12 个月内有效 Edition。不达标就不开——**宁可 5 个实频道，不要 20 个空壳** |
| AI 板块 | ⚠️ **改** | 不做"AI 驱动推荐"（冷启动 0 数据必崩，且黑箱破坏"可核查"人设）。做**结构化聚合**：AI 赛事（Kaggle/天池/DataFountain/百度之星）、AI 岗位（仅跳转）、AI 课程（仅高校公开课，**不接返佣**） |
| 招聘跳转 | ✅ 采纳，加边界 | 只索引公开官方招聘页；卡片固定六要素（企业/岗位/地点/**来源站点**/原始发布时间/抓取时间）；按钮统一"去原站投递"；**产品上物理不存在站内申请表单**——这比任何免责声明都硬。**一旦做投递闭环就撞《网络招聘服务管理规定》的人力资源服务许可证** |
| 移动端 | ✅ 采纳 | **响应式 Web 优先 + PWA 增强**。理由：入口在微信群/QQ 群，点开即浏览器；微信内置浏览器不支持安装。真正的留存抓手是 **.ics 日历订阅**，不是 App |
| 桌面端封装 | ❌ **不做** | Tauri/Electron 成本 2x、安装门槛极高、包体 5-150MB、需签名，而这个产品的使用场景（一年 40 天、手机上查截止日）与桌面完全错配。**收益为负** |

## 九、合规红线（一次性说清）

| 法规 | 触发条件 | 对策 |
|---|---|---|
| 《网络招聘服务管理规定》 | 做投递、收简历、企业付费发岗、撮合 | **只导流不闭环**：卡片只有"去原站"，无站内表单 |
| 《互联网新闻信息服务管理规定》 | 做时政/评论/深度栏目 | 不做评论栏目；摘要只陈述事实要素，不加观点 |
| 《生成式 AI 服务管理暂行办法》 | 站内 LLM 摘要直接面向公众且未经人工签发 | AI 只做**内部辅助抽取**；对公众展示须标"AI 辅助整理，以官方原文为准" |
| 《个人信息保护法》 | 获奖名单、录用公示含姓名/身份证 | **绝不入库任何个人身份信息**，名单类只做外链 |
| 《著作权法》 | 全文转载公告/大纲/职位表 | 标题照录、**正文不落地**、摘要自写 ≤80 字、附件只存 URL |
| ICP + 公安联网备案 | 国内云 80/443 上线 | **M1 前置条件**，别等上线才发现 |

**一句话版本**：**只做索引不做镜像；只给事实不给观点；只导流不闭环。**

## 十、最终结论

### 该做的

1. **用 AIHOT 的模板起仓库**（MIT、11340★、Docker 一键起），省掉 70% 从零开发
2. **砍到"3 门考试 × 1 所学校 × 1 个赛季 × 一个 .ics 链接"**，8 周内验证 200 人订阅
3. 把"信息来源可靠"做成**唯一可验证的产品特征**：每条强制四要素（来源链接/抓取时间/可信等级/纠错入口）
4. 把"自动化"预期定成 **"降低录入成本 70%"**，不是"无人值守"
5. 专业板块**按职业出口划分**，用"≥8 个 Program"做上线闸门防空页
6. 招聘**只做外链**，永不闭环

### 绝对不能做的

1. ❌ 一次做全量（20 个学院 + 全品类考试 + AI 板块 + 招聘 + App + 桌面端）
2. ❌ 靠内容流量变现（这个赛道所有走这条路的都变成了软文站）
3. ❌ 做"全自动发布"（核心字段错一次的代价远大于慢一天）
4. ❌ 做站内投递/代收简历（资质 + 法律责任）
5. ❌ 把 Star 数当成功指标

### 一句话总结

> **这个项目的护城河不是"信息聚合"，是"敢于为每一条信息标注它有多不确定"。**
> 前者任何爬虫都能做，后者需要一套制度、一套代码约束和一个人的长期值守。
> 先用 8 周证明"有人愿意把截止日记进日历"——如果连这个都没有，剩下的都是自嗨。
