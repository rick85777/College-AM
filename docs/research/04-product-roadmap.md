# College-AM 产品路线：信息架构、MVP 边界、开源治理与增长

> 定位一句话：**不做内容生产，做"什么时间、什么事、去哪报名"的结构化索引 + 日历订阅。**
> 判断标准：任何功能，如果不能回答"这条信息从哪来、什么时候抓的、准不准"，就不做。

---

## 1. 信息架构

### 1.1 一级导航（5 个，不加第 6 个）

`考证` / `竞赛` / `AI 板块` / `专业频道` / `招聘（外链）`

二级只出现在页内。辅助入口三个放顶栏与页脚：`日历`、`订阅`、`关于与数据来源`。移动端底部 Tab：首页 / 日历 / 考证 / 竞赛 / 我的订阅（"专业频道"收进首页宫格）。

### 1.2 四类实体与字段

| 实体 | 含义 | 必填字段 | 约束 |
|---|---|---|---|
| **Program** | 考试 / 赛事 / 招聘渠道本体（跨年不变） | id、kind(cert\|contest\|job)、name、aliases[]、organizer、organizer_type、level(国际/国家/省/校)、tags[]、majors[]、official_url、summary(≤80 字自撰)、status | summary 自写，禁止全文转载公告 |
| **Edition** | 某一届 / 某一次开放（带时间） | id、program_id、year、round、signup_start、signup_end、event_dates[]、fee、venue、notice_url、source_id、fetched_at、confidence(0-100)、review_state、diff_summary | 时间字段允许为空但必须标 `unknown`，不允许猜 |
| **Source** | 信源 | id、name、url、tier(L1-L4)、robots_ok、fetch_mode(static/js/api/rss)、last_ok_at、fail_count | L4 用户投稿不得单独成为 Edition 的唯一来源 |
| **Major** | 专业 / 方向 | id、name、aliases[]、related_programs[{program_id, weight(core/recommended/adjacent)}] | 无 core 关系不得开频道 |

> 数据模型与抓取链路的工程细节见 `03-auto-update-architecture.md`；本文只定义产品侧可见字段。

**硬规则**：每个详情页固定区块显示「来源链接 / 抓取时间 / 可信等级 / 上次人工复核 / 信息有误？」。过期条目变灰加"已结束"角标但**不删除**，保住 SEO 与历史查询。

### 1.3 页面清单

| 路由 | 页面 | 核心内容 | 关键交互 |
|---|---|---|---|
| `/` | 首页 | 近 30 天"正在报名"卡片流、本周截止倒计时、5 个频道入口 | 一键加日历、按身份筛选（年级/专业） |
| `/calendar` | 日历视图 | 月视图 + 学期视图（3-7 月 / 9-1 月），色块区分报名期/比赛期 | 导出 .ics、按 tag 过滤、订阅链接 |
| `/certs` `/certs/[slug]` | 考证列表 / 详情 | 按"报名中/即将开始/已结束"分组；详情含时间轴、费用、报考条件、大纲跳转 | 关注、加日历、纠错 |
| `/contests` `/contests/[slug]` | 竞赛列表 / 详情 | 同上，额外显示队伍规模、是否需校内选拔、往届题目外链 | 组队信息（仅外链到官方群） |
| `/ai` `/ai/[slug]` | AI 板块 | 三个 Tab：AI 赛事 / AI 岗位 / AI 课程与工具 | 方向标签过滤（CV/NLP/多模态/Agent/推理部署） |
| `/majors/[slug]` | 专业频道 | 300 字人工导读 + 该专业的 core/recommended 证赛清单 | 切换频道、订阅该频道 |
| `/jobs` | 招聘跳转 | 岗位卡片列表，只展示不投递 | "去原站"外链、按来源/城市过滤 |
| `/subscribe` | 订阅与提醒 | 邮件 / Web Push / .ics 三种，按 tag 与频道订阅 | 生成个人日历链接、退订 |
| `/sources` | 数据来源与更正 | 全部信源清单、层级、最近成功抓取时间、失效率 | 提交纠错、提交新信源 |
| `/about` | 关于 / 开源 | 项目定位、License、贡献方式、免责声明、联系方式 | 跳 GitHub |
| `/search` | 搜索 | 中文分词 + 别名召回（"软考"↔"软件水平考试"） | 结果内按类型聚合 |

## 2. 专业板块：为什么不能按学院切

**根因**：学院是组织单元，不是需求单元。三个问题会让"20 个学院"全是空页：

1. **同质化**。多数学校的"信息工程学院"就是"计算机学院"改名，"软件学院"常是同一套师资的另一块牌子，按学院建会造出 3 个 90% 重复的频道。
2. **证书跨院**。软考、四六级、大创对 20 个学院都相关；按学院切就得复制 20 份。
3. **院内分化**。同一个计算机学院里，走开发和走算法关注的东西完全不同，学院名无法区分。

### 2.1 划分原则（四条，可执行）

1. **按"出口"而非"入口"划分**。先定义 12-15 个职业出口画像（考公考编、保研、后端、算法、嵌入式/硬件、测试运维、网络安全、产品、设计、财会、教师、医护），频道 = 出口画像的别名集合，学院名只是频道的 `aliases`。
2. **多对多映射，不做树**。`Major ↔ Program` 带权重三档：core（本方向必考）、recommended（强烈建议）、adjacent（沾边）。一个 Program 可挂 N 个频道，但**必须至少有一个 core 关系**，否则不进任何频道页，只存在于搜索与标签层。
3. **上线闸门**（防空页硬指标）：频道上线需 ≥8 个 Program（≥3 证 + ≥5 赛），其中 ≥60% 有 12 个月内的有效 Edition。不达标不开——宁可 5 个频道，不要 20 个空壳。
4. **频道页不生产新内容**，只做过滤视图 + 300 字人工导读（"大一大二干什么、大三考什么"）。导读是频道唯一差异化，必须署名 + 标日期。

### 2.2 示例映射（注意：这三个学院名应先做 alias 合并，而不是建三个频道）

| 证 / 赛 | 计算机学院 | 软件学院 | 信息工程学院 |
|---|---|---|---|
| 软考（软件设计师 / 系统架构设计师） | core | core | recommended |
| 软考（网络工程师 / 信息安全工程师） | recommended | adjacent | **core** |
| NCRE 二/三/四级 | recommended | recommended | core |
| CCF CSP 认证 / PAT 甲级 | core | core | adjacent |
| 蓝桥杯（软件/电子类） | core | core | core |
| ACM-ICPC / CCPC / 天梯赛 | core | recommended | adjacent |
| 中国大学生计算机设计大赛 | recommended | core | recommended |
| 服务外包创新创业大赛 | recommended | core | adjacent |
| 全国大学生电子设计竞赛 | adjacent | adjacent | **core** |
| 睿抗 RAICOM / 嵌入式类 | adjacent | adjacent | core |
| 华为 HCIA/HCIP-Datacom | recommended | adjacent | **core** |
| 全国大学生数学建模竞赛 | recommended | recommended | core |
| 大创 / 挑战杯 / "互联网+" | core | core | core |

**内容来源（三条，缺一不可）**：① 目标院校培养方案与学位授予细则中的"职业资格/创新学分"条款——决定 core 标签，唯一权威依据；② 招聘 JD 中"证书优先"字段的反向计数——只统计不转载，校准 recommended；③ 学生投稿 + 共建人署名——补前两条的盲区。严禁"凭感觉推荐"。

## 3. AI 板块：做聚合，不做推荐

**结论：MVP 做"AI 相关事物的结构化聚合"，不做"AI 驱动的个性化推荐"。**

三条理由：
- 推荐需要用户画像与行为数据，冷启动期是 0，质量必崩，且让首页变成不可解释的黑箱，直接破坏"可核查"人设。
- AI 领域的真痛点是**更新快、生命周期短**（一个 AI 赛事从发布到截止常只有 3 周），聚合 + 时间轴的价值远大于"猜你喜欢"。
- AI 更适合放在**后台**：字段抽取、实体归一、变更摘要，而不是前台产品。

**最小可行形态**：`/ai` 三个 Tab，全走同一套 Program/Edition 模型，不另建表。
- AI 赛事：Kaggle、天池、DataFountain、百度之星、华为昇腾、计算机设计大赛 AI 赛道；
- AI 岗位：只跳转，分"实习/校招/日常"；
- AI 课程与工具：限高校公开课与官方文档，**不收付费课程、不接返佣**。

每条带方向标签（CV / NLP / 多模态 / Agent / 推理部署）。**中期才做**基于订阅行为的规则型提醒（"你订阅了 NLP，本周有 2 个赛事截止"），仍不是模型推荐。

## 4. 招聘跳转：边界比功能重要

### 4.1 四条硬边界

1. **不自建投递、不收简历、不做简历解析、不存候选人联系方式。** 一旦介入投递链，身份就从"信息服务"变成"职业中介"，触碰人力资源服务资质问题。
2. 只索引**公开可见**的官方招聘页（企业校招官网、高校就业网）；聚合平台仅在"企业无官网入口"时兜底，并标注"跳转第三方"。
3. 不做代投、内推收费、简历优化、面试辅导。
4. 不加工薪资：来源页没写就不显示，不造"月薪 15-25K"这类标题。

### 4.2 防"变成中介"的产品化设计

- 岗位卡片固定六要素：企业名 / 岗位名 / 工作地 / **来源站点 + 图标** / 原始发布时间 / 抓取时间；
- 按钮统一为"去原站投递"，外链加 `rel="nofollow noopener"`，有返佣的加 `sponsored` 并注明；
- 列表页顶部常驻：「本站不参与招聘流程，所有投递均在企业官方渠道完成。」
- **产品上物理不存在站内申请表单**——这是最有效的边界，比任何免责声明都硬。

### 4.3 防死链

抓取时记 `url_status / checked_at`；在架岗位每日 HEAD 探测：404/410 立即下架并写 tombstone（留 30 天，统计该源失效率）；连续 3 次 5xx/超时 → 置灰"来源暂时不可达"；岗位 TTL：校招 60 天、实习 45 天、社招 30 天，到期下线待复核。**来源健康度看板**：单源 404 率 > 15% 自动停用——把"信息源可靠"做成可观测指标，而不是口号。

## 5. 移动端与桌面端

| 方案 | 开发成本 | 安装门槛 | 推送 | 包体 | 审核 | 结论 |
|---|---|---|---|---|---|---|
| 响应式 Web | 1x | 零 | 无 | — | 无 | **M1 必做** |
| PWA（manifest + SW + Web Push） | 1.2x | 中（微信内不支持安装） | Android 好，iOS 需"添加到主屏" | 小 | 无 | **M1 做增强，不做渠道** |
| Capacitor 套壳 | 1.5x | 高（应用商店） | 完整 | ~10MB | 需 | M2 后视留存再定 |
| Flutter / RN 重写 | 3x | 高 | 完整 | 大 | 需 | 不做 |
| Tauri / Electron | 2x | 很高 | 桌面通知 | 5-150MB | 需签名 | **不做** |

**路径：Web（移动优先）→ PWA 增强 → 原生壳（可选）→ 桌面（不做）。**

三条理由：① 用户入口在微信群/QQ 群，点开就是浏览器，"打开即读完"比"装个 App"现实得多；② PWA 的收益是可安装 + 离线 + 推送，但国内 Android 浏览器碎片化、微信内置浏览器基本不支持安装，只能做增强；③ **真正的留存抓手是 .ics 日历订阅，不是 App**——把"四六级报名截止"导进手机自带日历，系统级提醒、零安装、跨端，性价比高一个量级，必须在 M1 完成。桌面端的"常驻 + 本地文件"与本项目不匹配，不做。

## 6. MVP 边界

### 6.1 第一版必须做（Definition of Done）

① 100 个 Program / 200 个 Edition，覆盖 5 个方向；② 列表 + 详情 + 日历 + .ics；③ 每条带来源/抓取时间/可信度；④ 搜索含别名召回；⑤ 375px 起可用；⑥ 可改数据的审核后台；⑦ 来源页 + 纠错入口；⑧ docker-compose 一键部署。

### 6.2 不做清单（10 条）

1. 不做注册登录（订阅用邮箱或匿名 token，不做账号体系）
2. 不做 UGC 投稿与评论（M2 再开）
3. 不做 AI 聊天助手、不用 AI 生成正文
4. 不做任何 App 壳（PWA 除外）
5. 不做招聘投递、不收简历
6. 不做付费、会员、广告位
7. 不做推荐算法与"猜你喜欢"
8. 不做多语言（只中文）
9. 不做"全国高校大全/专业大全"数据库（只做映射表）
10. 不做数据大屏与可视化图表、不做爬虫管理 UI（配置文件 + 告警足够）

### 6.3 里程碑

| 里程碑 | 周期 | 交付物 | 验收标准（不合格就不进下一阶段） |
|---|---|---|---|
| **M0 数据骨架** | 4-6 周 · 1 人 | schema v0.1、10 个信源、50 条 Program、抓取链路跑通、审核台可改数据 | 连续 14 天抓取成功率 >90%；抽检 20 条字段准确率 >95% |
| **M1 可用 MVP** | +6-8 周 · 1-2 人 | 100 Program/200 Edition、5 个频道、搜索、.ics、来源页、部署脚本 | 真实用户 100 人、周活 30、.ics 订阅 20、有 3 条真实纠错被处理 |
| **M2 社区化** | +3 个月 · 2-3 人 | 开放投稿与共建人制度、schema v1.0 冻结、贡献者 ≥5 | UGC 审核通过率 >60%、30 日留存 >15%、2 个频道有外部共建人 |

## 7. 开源治理

### 7.1 License：AGPL-3.0（代码）+ CC BY-SA 4.0（数据）

**理由**：护城河不是代码，是"持续维护的数据 + 品牌信任"。AGPL §13 的网络条款能挡住最常见的白嫖形态——部署一个一模一样的站、去掉来源标注、还不回馈。MIT/Apache 允许闭源衍生，对 1-3 人维护的项目不划算。

**取舍与缓解**：AGPL 会吓退部分企业贡献者和高校社团（学校法务可能不接受）。缓解靠**双许可**：默认 AGPL，作者保留商业授权（README 写明"校内与非商业使用无需申请"）。判断标准：想被大范围 fork 用于教学 → Apache-2.0；想防止"白嫖 SaaS" → AGPL-3.0。**本项目选后者**，另加 TRADEMARK 政策，禁止第三方以 "College-AM" 名义运营。

### 7.2 数据与代码分仓（三仓）

- `college-am/core`：应用代码，AGPL-3.0
- `college-am/data`：数据快照 + schema，CC BY-SA 4.0，每日 CI 导出分片 JSON（`data/2026/11/*.json`）
- `college-am/sources`：信源配置与抓取规则，独立仓

分仓三个好处：数据可被第三方复用、代码仓不被数据 diff 淹没、信源配置的合规审查可独立进行（有人只想加一个源，不该被迫读全站代码）。

### 7.3 贡献流程

三类入口：加信源（填 YAML）、改数据（Issue 表单）、改代码（PR）。用 **DCO**（`Signed-off-by`）而非 CLA——CLA 会让个人贡献者犹豫。PR 必过三道：schema 校验 + 链接可达性 + 1 名 maintainer review。贡献指南写清"数据贡献不等于版权让渡，贡献者保留署名权"。

Issue 模板四个：`data-error.yml`（哪条错、正确值、官方链接）、`new-source.yml`（名称/URL/层级/更新频率/robots 截图）、`dead-link.yml`（自动带 URL 与抓取时间）、`feature.yml`。

### 7.4 Schema 版本化

`schema_version` 用 `MAJOR.MINOR`，写在每个 JSON 文件头与 API 响应头。**MINOR**（加字段、加枚举值）不需要迁移，但文档必须写死"消费方应忽略未知字段"。**MAJOR**（删字段、改语义、改类型）必须提供 `migrations/vX_to_vY.ts`、旧版本导出保留 6 个月、CHANGELOG 写明改动理由。v1.0 在 M2 冻结；冻结前允许每周破坏，冻结后一年最多 1 次 MAJOR。

### 7.5 防白嫖的现实预期

法律层靠 AGPL §13；技术层在数据里嵌 `dataset_id` 与少量 canary 条目（可被搜到，用于举证）；社会层在 README 放"部署者名单"，把回馈变成荣誉。**目标是让正经做产品的人愿意署名，不是让盗用者跑不起来**——后者做不到。

## 8. 冷启动与增长

**0 → 1000 真实用户**（定义：7 日内至少 1 次有效行为，不是 UV）：

- **第 1 批 50 人**：自己学校 + 2 个学院群。不说"我做了个网站"，说"我把你们学院这学期能报的比赛整理成表了，要吗"。这批人既是种子用户也是校对员。
- **第 2 批 200 人**：3-5 个垂类群（软考、蓝桥杯、数模）。切入点是"截止日提醒"而非"信息聚合"，传播单元是**每群一张专属 .ics 链接**（`/calendar.ics?tag=lanqiao`），摩擦最低。
- **第 3 批 750 人**：SEO 长尾。"2026 年 X 考试报名时间"每个都是搜索词，详情页必须 SSR + schema.org/Event。GitHub 侧同步曝光：README 放 GIF 演示 + JSON 数据端点。

**关键指标不是 PV，是 .ics 订阅数。** 一个订阅 ≈ 一个长期留存。

**Star 现实预期（不吹）**：0-3 个月 50-150；3-12 个月 200-600（前提是 README 有演示、有 1 篇被转到 V2EX 或少数派）；一年后若无大 V 转发，大概率停在 1k 以内。**star 与真实用户几乎不相关**，很多 5k star 的聚合项目没有一个日活。把 star 当传播指标，不当成功指标。

**人力模型**：
- 1 人：维持 100-300 条，每周 6-8 小时（审核 + 修源），这就是上限，超 500 条必崩；
- 3 人（作者 + 1 数据 + 1 前端）：到 1000 条 + 10 个频道，各 4-6 小时/周；
- 社团共建（8-15 人）：看着最美，实际最难，学生一学期换一批，交接成本常高于产出。可行形态是**"频道共建人"**：一个社团只负责 1 个频道，签 1 学期，交 20 条数据 + 1 篇导读 + 交接文档。**不要指望社团写代码。**

结论：**按 3 人上限设计系统**（自动化优先、审核台好用），社团只做内容不做工程。

## 9. 商业化克制

**会毁掉信任的（不做）**：付费置顶/推荐位（一旦能被买排序，"可靠"人设就没了）；培训机构导流与返佣（最容易被出价，也最致命）；卖邮箱/用户数据；简历代收、内推收费；开屏与弹窗广告；"会员才能看截止日期"这类锁核心信息的做法。

**可以接受的（按推荐度）**：① 捐赠/赞助（GitHub Sponsors、爱发电），无权益差别；② 企业赞助"数据托管由 XX 提供"，不进内容区；③ API 商业授权（双许可，个人与教育免费）；④ 高校/机构定制部署（一次性收费，代码仍开源）；⑤ 实体周边（贴纸、日历卡），更像社区运营而非营收。

**底线**：任何影响"信息排序"和"信息完整性"的钱，都不能收。
